# PRD (제품 요구사항 문서) v0.1

- 버전: v0.1 (초안)
- 작성일: 2026-10-27
- 상태: 검토 전

## 1. 개요

- 프로젝트명: 전운시(전지적 운동 시점) — 운동이 전투가 되는 인증형 RPG
- 목적 (한 줄): 맨몸 운동을 꾸준히 하려는 10~20대가 카메라 자세 인식으로 운동 중 즉시 피드백을 받고, AI가 바로 판정한 운동 기록을 캐릭터 성장과 전투 리플레이로 이어갈 수 있게 한다
- 사용자 (한 줄): 맨몸 운동을 꾸준히 하려는 10~20대 (14세 미만 가입 불가)
- 개발 기간: 8주 (팀원 5명)

## 2. 사용자 여정

### 연결된 상태 전이
03-rules-states-llm.md의 핵심 대상: 운동 제출건 (WorkoutSubmission) — 플레이어가 운동 세션 하나를 끝낼 때마다 생기는 기록 1건
지나가는 상태: `SUBMITTED` 제출됨 → `PREPARED` 계산 완료 → `APPROVED` 승인 → `REWARDED` 지급 완료 (4개)

| 상태 | 뜻 | 누가 바꾸나 |
| --- | --- | --- |
| `SUBMITTED` 제출됨 | 운동이 끝나 기록이 접수됨 | 시스템 |
| `PREPARED` 계산 완료 | 보상과 타격 수가 계산되어 고정됨 | 규칙 엔진 |
| `APPROVED` 승인 | AI가 실제로 한 운동이라고 판단함 | AI 판정 (확신도 90% 이상) |
| `REWARDED` 지급 완료 | 보상이 한 번 반영되고 리플레이를 볼 수 있음 | 시스템 |

- 이 흐름은 AI 확신도가 90% 이상인 경우라 사람 확인 없이 바로 승인된다. 90% 미만이면 사람 확인(`PENDING_REVIEW`)으로 가며, 그 경로는 아래 '이 흐름에 포함하지 않은 경로'에 있다.
- 근거: 제안서 v2 Ⅳ-12, client-meeting-1 피드백 7·8, 질의응답 2, 03 3-2

### 이 흐름에 포함하지 않은 경로

- 취소·반려는 backlog.md의 필수 스토리 US-06(취소)·US-08(반려)에서 다룬다
  - 취소 (US-06): `SUBMITTED` / `PREPARED` / `PENDING_REVIEW` → `CANCELED` (승인 전 신청자 취소, 상한 예약 해제, 취소와 승인이 동시에 오면 먼저 성공한 한 건만 인정)
  - 반려 (US-08): `PENDING_REVIEW` → `REJECTED` → `CLOSED` (확인자가 사유 코드 `기록이상` / `본인확인실패` / `도용의심`과 설명을 남기고 반려. 카메라 세션은 재제출할 수 없어 `CLOSED`, 상한 예약 해제)
- 애매한 건의 사람 확인 (US-07): 확신도가 기준 미만이면 `PREPARED` → `PENDING_REVIEW` (신청자가 보낼 내용을 미리 보고 지인·길드장에게 보냄) → `APPROVED` / `REJECTED`. MVP에는 포함하지만 첫 데모에서는 제외
- 재제출 `REJECTED` → `SUBMITTED`: 연동 러닝 세션만 해당하고 러닝 연동이 후순위라 MVP에서는 없음 (제안서 Ⅳ-11 F-02)
- 신고·회수 `REWARDED` → `REVOKED`: F-07 선택 기능, MVP에서 제외 (mvp-scope.md)
- 접수 단계의 실패: 같은 시간대 활성 스쿼트 건이 있으면 접수 거부(R3), 일일 상한을 넘은 인정량은 기록만 남기고 보상·타격 0, 리플레이 없이 "일일 상한 초과" 카드(R1·R9)
- 시스템 실패: 계산 실패 시 `SUBMITTED` 유지 후 재시도, 지급 실패 시 `APPROVED` 유지 후 지급만 재시도 (03 3-2)
- 첫 데모에서 뺀 기능: 휴식 경고·경고 3회 공격 실패(F-11 일부), 오각형 성장 리포트(F-12), 나머지 운동·약점 배율, 걸음 수 체력 회복(F-09), 러닝 연동, 음성 인식(F-14), 숙련도 이펙트·보상 상자 연출 (제안서 Ⅰ-3 '이번에 하지 않는 것')

## 4. 기술 스택

`docs/STACK.md`의 '최종 선택'과 'LLM 연결'을 그대로 옮김. 후보 2안 비교, 선택 이유, 검증 계획, 확인할 것은 `docs/STACK.md`를 본다.

- 선택한 안: A안 (React Native + Expo 개발 빌드 앱 + FastAPI)
- 프론트엔드: React Native + Expo (TypeScript), 개발 빌드 사용, Android 우선
- 백엔드: FastAPI + SQLAlchemy (Python)
- DB: PostgreSQL
- UI 도구: NativeWind (React Native용 Tailwind)
- 테스트 방식: 백엔드 pytest + 실제 PostgreSQL(Docker Compose), 앱 Jest + React Native Testing Library(화면), Jest(렙 판정 로직), CI는 GitHub Actions로 PR마다 실행
- 시연·배포 환경: 개발은 Expo 개발 빌드, 시연은 JS 번들과 모델 파일이 포함된 서명된 Android APK를 직접 설치. 정확한 시연 빌드 명령·서명 설정은 실제 빌드 후 기록(EAS 내부 배포는 예비). 백엔드 Render Free, DB Neon Free. 막히면 개발자 PC 백엔드 + HTTPS 터널. 스토어 등록은 하지 않음
- 카메라·자세 인식: react-native-vision-camera + react-native-fast-tflite(TFLite 자세 모델)로 시작. 3주차 첫 데모 전에 MediaPipe(커뮤니티 Expo 모듈 또는 Kotlin 네이티브 모듈)와 비교
- LLM: 제공사·모델 미정(기존 Gemini 안은 연령 조건 검토로 보류). 백엔드에서만 호출하며 구현 중에는 모의 응답으로 연결을 검증
- LLM 연결: LLM(L1 기록 요약, L2 이상치 설명, L3 전투 서사, L4 자세 교정 코멘트)은 **FastAPI 백엔드에서만** 호출하고(앱에 키를 넣지 않음), 상태 전이는 **백엔드 규칙과 사람(확인자)만** 결정한다. 출력은 `ai_summary`·`ai_flags`·`ai_story`·`ai_form_tip`에 저장만 하고, 실패하면 기본 문구로 진행한다.

## 7. 상태와 LLM의 역할

- 상태 전이: 정상 경로 `SUBMITTED` → `PREPARED` → `APPROVED`(AI 판정) → `REWARDED`. 확신도 기준 미만이면 `PREPARED` → `PENDING_REVIEW` → `APPROVED` / `REJECTED` → `CLOSED`. 승인 전 `SUBMITTED` / `PREPARED` / `PENDING_REVIEW` → `CANCELED`. 판정을 건너뛰는 `SUBMITTED` → `APPROVED`는 허용하지 않음. (user-flows.md, backlog.md, 03 3-2 기준)
- LLM이 맡는 일: L1 기록 요약(`ai_summary`), L2 이상치 설명(`ai_flags`), L3 전투 서사(`ai_story`), L4 자세 교정 코멘트(`ai_form_tip`). L5 성장 리포트는 MVP 제외
- 상태를 바꾸는 결정을 하는 곳 (규칙 / 사람): 규칙 — 운동 종류별 판정 기준, 무작위 동작 확인, AI 판정 확신도 기준(90%)으로 `PREPARED → APPROVED`. 사람 — 확신도 기준 미만 건에서 확인자(지인·길드장)가 승인 또는 반려. LLM 출력은 상태를 바꾸지 않고, 확인자가 승인이나 반려를 누르기 전까지 `PENDING_REVIEW`는 바뀌지 않음
- LLM에 보내지 않을 정보: L3·L4 — 수치·메모·관절 좌표 원본·얼굴 정보·닉네임·길드명. L1·L2 — 닉네임·길드명, 메모 속 이름·연락처·장소, 관절 좌표 원본(통계로만 보냄), 건강 앱 원본 데이터 (제안서 Ⅳ-13)

## 9. 디자인 방향

- 분위기: 검은 배경에 형광 라임색으로 강조하는 대비가 강한 다크 테마. 사람 몸 실루엣에서 운동한 부위를 색으로 채워 보여 주고, 선택 항목은 둥근 알약 모양 버튼으로 표시한다. 스포티하고 깔끔한 느낌 (팀 참고 이미지: 근육 부위 선택 화면)
- 주 색상: `#B9FD50` (형광 라임: 강조, 선택 상태, 주요 버튼), `#000000` (배경)
- 참고 서비스: 플랜핏 (근육 회복·근육 균형을 보여 주는 대시보드, 운동 영상 가이드), Fitbod (근육 피로도 분석, 맨몸 운동 지원), Fitness AI (근육 그룹 강조 표시)
- 반응형 여부: 모바일 앱 (React Native, Android 우선). 웹은 만들지 않음 (docs/STACK.md)

## 10. MVP 범위와 제외

- MVP 포함: US-01 운동하면 렙을 세어 자동 제출(스쿼트), US-02 보상·타격 수 미리보기, US-03 AI 확신도 기준 이상이면 바로 승인, US-04 보상을 한 번만 반영, US-05 리플레이·결과 카드·교정 코멘트 보기, US-06 승인 전 제출 취소, US-07 애매한 건을 지인·길드장에게 확인 요청, US-08 확인자가 사유와 함께 반려, (US-01~05의 전제) 회원·캐릭터·길드(F-01)
- 이번에 제외 (이유 포함):
  - 신고·회수 (F-07, `REWARDED → REVOKED`): 스토리 8개 상한 안에서 확인 요청·반려(US-07·08)를 먼저 넣음. 이미 쓴 아이템의 롤백 범위가 정해지지 않아 인수 조건을 쓸 수 없음 ('여전히 가정' 5행)
  - 스쿼트 외 운동(푸시업·플랭크 등)과 약점 배율: 운동마다 판정 기준·촬영 각도 테스트가 필요하고, 고객이 답한 일일 상한이 스쿼트·러닝뿐이라 경계값이 정해지지 않음. 스쿼트 1종의 인식 정확도를 먼저 확보함 (피드백 6). 일정이 남으면 M2에서 추가
  - 휴식 경고·경고 3회 초과 시 공격 실패 (F-11 일부): 기준 시간이 정해지지 않았고, 공격 실패 때 운동 기록을 지우면 "운동은 헛되지 않는다" 원칙과 충돌함 ('여전히 가정' 6행)
  - 오각형 성장 리포트 (F-12, LLM L5): 다섯 번째 축이 정해지지 않음 ('여전히 가정' 4행). LLM 가치에 대한 고객 요청(피드백 12)은 필수 기능인 자세 교정 코멘트(F-13)로 먼저 대응함
  - 걸음 수 체력 회복 (F-09): 건강 앱 연동이 필요한데, 같은 연동인 러닝이 후순위로 정해짐 (질의응답 6). 체력이 없어도 핵심 흐름(제출→지급→리플레이)은 돌아감
  - 건강 앱 러닝 연동과 재제출 (`REJECTED → SUBMITTED`): 고객이 러닝은 기존 앱이 많아 우선순위가 낮다고 함 (질의응답 6). 재제출은 연동 세션에만 해당하므로 함께 빠짐
  - 음성 인식 (F-14): 부가 기능. 시끄러운 곳에서 불안정할 수 있고, 목표 개수·세트를 먼저 정하는 방식으로 운동 중 조작이 필요 없음 (피드백 18)
  - 숙련도 이펙트·보상 상자 연출: 고객이 게임 요소는 가볍게 하라고 함 (피드백 1·2). 수치와 리플레이만으로 결과가 전달됨
  - 스킬 연계 콤보, 여러 지역·막타 보너스: 5명·8주 안에서 게임 요소의 비중을 낮추고 자세 인식에 시간을 쓰기 위해 (피드백 1)
  - 거래·강화·제작, 직업, 길드 채팅, 자유 대화형 NPC: 운동 지속과 직접 관련이 없고 구현 범위가 큼 (피드백 1·2)
  - GPS 경로·심박 수집, 웨어러블 직접 연동: 동의 범위를 넘는 건강·위치 정보를 모으지 않기 위해 (03 R17)
  - 검토용 3D 모델링: 작업량이 큼. 관절 선 또는 실루엣으로 얼굴 없이 확인할 수 있음 (피드백 19)
  - 고도화된 도용 탐지: 시작 시 무작위 동작 확인과 사람 확인·신고로 1차 대응. 탐지 기준을 세울 데이터가 아직 없음
- 시연용 단순화와 제약: 첫 데모(3주차)는 스쿼트 30회 정상 경로 하나(`SUBMITTED` → `PREPARED` → `APPROVED` → `REWARDED`)만 보여 준다. 지급 요청을 두 번 보내도 한 번만 반영되는 것과 LLM을 꺼도 기본 문구로 `PREPARED`까지 가는 것을 함께 확인한다. 취소·사람 확인·반려 경로(US-06~08)는 첫 데모 뒤에 만든다
